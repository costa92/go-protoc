# 需求文档 - Makefile统一入口安装脚本重构

## 介绍

当前项目的服务部署管理存在多个入口点、不一致的调用方式和分散的配置管理，导致维护复杂性高、新服务添加困难。本重构项目旨在建立统一的Makefile入口，标准化Docker容器启动流程，集中管理配置文件，并提供一致的错误处理和健康检查机制。

## 需求

### 需求 1 - 统一用户入口

**用户故事：** 作为系统运维人员，我希望通过单一的Makefile入口管理所有服务，这样我就可以使用一致的命令格式，减少学习成本和操作错误。

#### 验收标准

1. WHEN 用户需要安装任何服务 THEN 系统应当只提供 make 命令作为入口点
2. WHEN 用户执行 `make deploy.install.docker.<service>` THEN 系统应当启动对应的Docker服务
3. WHEN 用户使用现有的 make 命令 THEN 系统应当保持100%向后兼容性
4. WHEN 用户查看帮助信息 THEN 系统应当显示统一格式的命令说明

### 需求 2 - Docker容器启动标准化

**用户故事：** 作为开发人员，我希望所有服务都使用标准化的Docker启动函数，这样我可以确保所有容器具有一致的配置和行为。

#### 验收标准

1. WHEN 任何服务需要启动Docker容器 THEN 系统应当使用 `proj::docker::run_service()` 统一函数
2. WHEN Docker容器启动 THEN 系统应当自动配置标准参数（network, restart policy, naming convention）
3. WHEN 容器启动失败 THEN 系统应当提供统一的错误处理和日志记录
4. WHEN 清理容器 THEN 系统应当使用一致的清理逻辑

### 需求 3 - 配置文件管理集中化

**用户故事：** 作为系统管理员，我希望所有服务配置都通过统一的变量和模板系统管理，这样我可以轻松地自定义和维护配置。

#### 验收标准

1. WHEN 系统需要服务配置 THEN 系统应当使用 PROJ_*_CONFIG_DIR 环境变量定义配置目录
2. WHEN 生成配置文件 THEN 系统应当使用 `proj::config::render_service_template()` 函数从模板生成
3. WHEN 配置依赖其他服务 THEN 系统应当自动注入服务发现变量
4. WHEN 配置文件不存在 THEN 系统应当自动创建必要的目录结构

### 需求 4 - 健康检查和重试机制

**用户故事：** 作为运维工程师，我希望所有服务都有标准化的健康检查和自动重试机制，这样我可以确保服务的可靠性和自动恢复能力。

#### 验收标准

1. WHEN 服务启动后 THEN 系统应当自动执行健康检查验证服务可用性
2. WHEN 健康检查失败 THEN 系统应当使用指数退避策略进行重试
3. WHEN 重试次数达到上限 THEN 系统应当记录详细错误信息并返回失败状态
4. WHEN 不同类型的服务 THEN 系统应当使用相应的健康检查方法（HTTP、TCP、Redis ping等）

### 需求 5 - 服务依赖管理

**用户故事：** 作为开发者，我希望服务启动时能自动检查和管理依赖关系，这样我可以确保服务按正确顺序启动并具备所需的依赖。

#### 验收标准

1. WHEN 服务声明依赖其他服务 THEN 系统应当在启动前验证依赖服务状态
2. WHEN 依赖服务未启动 THEN 系统应当提供清晰的错误信息和建议操作
3. WHEN 服务需要依赖服务端点信息 THEN 系统应当自动注入端点配置
4. WHEN 批量操作多个服务 THEN 系统应当按依赖关系确定启动顺序

### 需求 6 - 标准化工具库

**用户故事：** 作为脚本维护者，我希望有标准化的工具函数库，这样我可以重用通用功能，减少代码重复并提高维护效率。

#### 验收标准

1. WHEN 需要Docker操作 THEN 系统应当提供 `docker_helper.sh` 工具库
2. WHEN 需要配置管理 THEN 系统应当提供 `config_manager.sh` 工具库  
3. WHEN 需要健康检查 THEN 系统应当提供 `health_check.sh` 工具库
4. WHEN 需要重试逻辑 THEN 系统应当提供 `retry.sh` 工具库

### 需求 7 - 新服务添加简化

**用户故事：** 作为开发团队成员，我希望添加新服务的过程标准化且简单，这样我可以快速集成新服务而不需要学习复杂的配置过程。

#### 验收标准

1. WHEN 添加新服务 THEN 系统应当提供标准的服务脚本模板
2. WHEN 新服务需要配置 THEN 系统应当支持模板化的配置文件
3. WHEN 新服务集成到Makefile THEN 系统应当遵循一致的命名和调用规范
4. WHEN 完成新服务添加 THEN 时间应当从2小时减少到30分钟以内

### 需求 8 - 错误处理和日志记录

**用户故事：** 作为系统调试人员，我希望有统一的错误处理和日志记录机制，这样我可以快速定位和解决问题。

#### 验收标准

1. WHEN 任何操作发生错误 THEN 系统应当提供清晰的错误信息和建议解决方案
2. WHEN 执行长时间操作 THEN 系统应当提供进度反馈和状态更新
3. WHEN 操作成功完成 THEN 系统应当提供成功确认和关键信息摘要
4. WHEN 调试问题 THEN 系统应当支持详细的调试日志选项
